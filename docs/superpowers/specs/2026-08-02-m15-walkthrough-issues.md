## 问题 1：撤销上一刀 — 始终从第一页最后一刀开始撤销（重要 bug）

### 现象
在多页 PDF 裁切时，点"撤销上一刀"按钮，不管当前在第几页，总是从**第一页**的最后一刀开始撤销，依次退到第一页所有刀撤完，之后点击无任何反应。第二页及后续页的刀无法用撤销按钮撤掉。

### 期望
撤销上一刀应作用于**当前可见页**（`activePage`）：如果当前在第 3 页，则撤销第 3 页最后一刀；如果第 3 页无刀，给个提示或无反应（当前已经是无反应，但用户不知道为什么）。

### 根因分析（待技术手册确认）
当前 `CropView.tsx` 中按钮的 `onClick` 是：
```tsx
onClick={() => activePage && crop.undoLastCutLine(activePage.id)}
```
`activePage` 应该是当前可见页，但实际似乎始终是第一页。怀疑 `activePage` 的跟踪逻辑有问题——`onVisiblePageChange` 回调依赖 PDFViewer 的 IntersectionObserver 触发，但可能在多页时没有正确更新，导致 `activePageId` 始终停留在初始值（第一页）。

### 影响
高：这是裁切页最常用的操作。用户错切后无法快速撤销，只能靠"排除框"模式绕过，体验很差。

### 涉及文件
- `src/renderer/src/views/CropView.tsx`（activePageId / onVisiblePageChange）
- `src/renderer/src/views/PDFViewer.tsx`（onVisiblePageChange 触发时机）

## 问题 2：框选片段只支持自动对齐，需增加手动拖动调整模式

### 现象
框选工具选出题目的一部分后，片段只能按「上下自动对齐拼接」的方式合并入题，导致跨列或位置偏移的情况下图片内容错位，无法精确对准。

### 期望
增加一个**手动微调模式**，允许用户在后期处理阶段（或框选后）拖动各段的相对位置（上下偏移），使拼合图更精准。

### 现状与约束
- 当前拼合逻辑（`composeQuestionCanvas`）严格纵向居中对齐：较窄段水平居中，无纵向偏移控制。
- `question_segments` 表记录 `merge_order`（纵向顺序），但无 `y_offset` 等微调字段。
- 这是一个较大的 UX 改动，需要：
  1. DB/DTO 层加 `y_offset`（或类似字段）
  2. 拼合函数支持偏移参数
  3. 后期处理页加拖动手柄 UI

### 优先级
中：解决方法上用户目前可以通过重新框选更精准的区域来规避，但对于排版复杂的试卷（多列交叉）影响较大。

### 涉及文件
- `src/renderer/src/services/QuestionRenderService.ts`（composeQuestionCanvas）
- `src/main/storage/repositories/questionRepo.ts`（question_segments 表结构）
- `src/renderer/src/views/PostProcessView.tsx`（合并操作 UI）

## 问题 3：完成全流程后没有结束提示，用户不知道流程已完成

### 现象
答案匹配确认绑定后，页面停在答案匹配页，没有任何"全部完成"的提示或自动跳转。用户以为操作没有成功或流程没结束。

### 期望
确认绑定成功后，给出明确的完成反馈：
- 方案 A（轻量）：Toast 通知"答案绑定完成，该试卷全部流程已完成"，并在顶栏显示绿色"已完成"标记。
- 方案 B（中量）：弹出一个完成总结 Modal，显示试卷名、入库题数、绑定答案数、出处年份，底部"返回主页"和"前往题库"两个按钮。
- 方案 C（大改）：专门的"完成页"路由（/complete/{paperId}），显示试卷摘要 + 导出快捷入口。

### 建议
方案 B（中量 Modal）。理由：够清晰、代价低（不加新路由），用户看到题数和答案数就能确认"确实完成了"，两个按钮提供明确的下一步。

### 优先级
中：不影响功能，但严重影响使用体验的闭环感。首次使用的用户必然困惑。

### 涉及文件
- `src/renderer/src/views/AnswerMatchView.tsx`（handleConfirm 成功后的逻辑）
