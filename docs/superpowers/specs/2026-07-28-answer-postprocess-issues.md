# 答案卷后期处理 + 匹配流程对齐（需求）

- 日期：2026-07-28
- 提出人：用户（M14 人测后）
- 关联：`2026-07-26-m14-answer-solution.md`（M14 技术手册）、`2026-07-06-development-progress.md` 5.10/5.11
- 性质：M14 的流程补全，不是新里程碑。暂记为 **M14.5**。

---

## 背景

M14 已实现"导入答案 PDF → 裁切 → 答案匹配 → 绑定答案图"，人测功能可用。但答案侧的处理流程与题目侧**不对称**：

| 环节 | 题目卷 | 答案卷（现状） |
|---|---|---|
| 导入 | ✅ | ✅ |
| 裁切（横切/框选） | ✅ | ✅ 完全复用 |
| **后期处理（删除/合并）** | ✅ | ❌ **没有这一步** |
| 匹配/入库 | 入库出图 | 在匹配页勾片段配对 |

答案卷裁完直接跳答案匹配页（`CropView.tsx:56-58` 按 `kind` 分流到 `/answer/{parent_paper_id}`），中间缺了后期处理环节。

---

## 问题 1：答案片段无法删除

**现状**：答案 PDF 裁切后产生的所有片段，全部原样进入答案匹配页的候选网格。

**问题**：答案 PDF 上普遍存在无关内容——页眉、页脚、"参考答案"大标题、装订线区域、页码、空白栏。这些被横切/框选切出来后成为独立片段，混在候选网格里。用户只能视而不见，没法删掉。

**期望**：答案片段可以软删除，删掉后不出现在匹配页的候选网格里。已删除的能恢复。

**涉及**：`segments.is_deleted` 字段已存在，IPC `segments:setDeleted` 已存在（`ipc/index.ts:181`），仅缺 UI 入口。

---

## 问题 2：跨页答案无法合并成一个整体

**现状**：一道大题的答案跨页时（上半在第 1 页底部，下半在第 2 页顶部），裁出来是两个独立片段。匹配页支持一题勾多段（`AnswerMatchView` 的 `togglePairing` + `segmentIds` 数组），确认绑定时会纵向拼合成一张图，所以**结果是对的**。

**问题**在于操作过程：候选网格按 `(page_index, order_index)` 排序（`deriveAnswerItems`），跨页的两段之间隔着第 1 页剩下的所有片段。用户要在网格里找到"答案 7 的上半"和"答案 12 的下半"并同时勾选，靠肉眼比对，很容易错。而且每次给不同题配对时都要重新勾一遍这两段。

**期望**：在后期处理阶段就把这两段合并成一个"答案单元"，之后在匹配页里它显示为**一个**缩略图（纵向拼合的整体），一眼就能确认这是完整答案。合并关系持久化，匹配时只需勾这一个单元。

**涉及**：题目侧的合并机制（`question_segments` 表 + `createQuestionWithSegments` + `merge_order`）已完整可用。

---

## 问题 3：答案编号错位

**现状**：`deriveAnswerItems` 给每个未删除片段按视觉顺序编 `answerNumber`（1、2、3…），匹配页显示"答案 1""答案 2"。

**问题**：只要答案 PDF 上有任何无关片段（问题 1）或有跨页答案（问题 2），这个编号就和真实答案题号错位。用户看到"答案 5"，实际可能是第 3 题的答案。自动配对（`autoPairAnswers` 按序号一一对应）也因此大面积配错，得手工全部重配。

**期望**：删掉无关片段、合并跨页答案之后，答案单元的序号自然与真实答案题号对齐，自动配对的命中率大幅提升。

---

## 期望的流程

```
导入答案 PDF → 裁切 → 【答案后期处理】→ 答案匹配 → 确认绑定
                        ↑ 新增这一步
                        删无关片段、合并跨页答案
```

用户明确要求：**答案的后期处理界面与题目卷保持一致**（同样的删除、合并、撤销、缩略图缩放操作），降低学习成本。

用户同时提到"在此页支持与题目匹配，可选匹配"——即后期处理页可以顺手做匹配，也可以跳过、留到下一步统一做。这条**本轮不实现**，理由见下方"本轮不做"。

---

## 本轮不做（明确排除）

1. **后期处理页内做匹配**：匹配需要同时看到题目和答案两侧，塞进后期处理页会让该页承担两种职责，且 `PostProcessView` 已有 1100+ 行（进度文档 M17 已列为待拆分对象）。保留"匹配只在答案匹配页做"的单一入口。用户的"可选匹配"诉求由现有的自动配对 + 手动调整满足。
2. **答案卷入库出图**：答案单元不需要独立的 PNG 文件。答案图仍在匹配确认时按绑定关系渲染，写到 `questions.answer_image_path`（题目行上）。答案卷不产生 `image_path`。
3. **答案单元的标签/题型**：答案不需要章节、难度、知识点、题型。

---

## 红线提醒

1. **五张几何表不动**：`pages` / `column_dividers` / `cut_lines` / `segments` / `manual_boxes` 的结构和语义零改动（M14 原红线）。
2. **不新增表**：合并关系复用 `question_segments`。
3. **`questions.answer_image_path` 语义不变**：它挂在**题目**行上，表示"这道题的答案图"。答案卷的 question 行不写这个字段。
4. **答案卷的 question 行绝不能进题库**：`listBankQuestions` 是全库扫描（`questionRepo.ts:59`），必须显式按 `papers.kind = 'paper'` 过滤。当前靠 `image_path IS NOT NULL` 意外挡住了，属于巧合防护，不可依赖。
5. **`derivePreviewItems` / `derivePreviewQuestions` 纯函数不动**：题目侧行为零变化，答案侧复用同一套推导。
6. **`(page_index, order_index)` 排序键不动**：题目侧和答案侧共用这个口径（`PostProcessService` / `AnswerMatchService` / `handleFinalize` 三处已严格一致）。
7. **`handleFinalize` 不能对答案卷跑**：它会写 `image_path`、`setPaperStatus(pid,'done')`、套题型模板，这些对答案卷都是错的。
8. **A12 先写库再更新 state**。

---

## 一句话总结

答案卷缺后期处理环节，导致无关片段删不掉、跨页答案合不了、答案编号与真实题号错位；本轮给答案卷补上与题目卷一致的后期处理界面（删除 + 合并 + 撤销），让答案单元在匹配页显示为一个整体。
